1-B · District Level — Full Fallback & Secure Deployment

5-node setup. Full database failover, HA load balancer, encrypted disks, VPN admin access, WAF. Handles a district going fully live with all PS.

#NodeCPURAMStorageRole
1 LB / Bastion 2 vCPU 5 GB 60 GB SSD nginx + ModSecurity WAF, SSL termination (Let's Encrypt / NIC CA), Fail2ban, WireGuard VPN jump host
2 App Server 1 5 vCPU 10 GB 96 GB SSD Node.js PM2 primary (5 workers), RabbitMQ, Redis
3 App Server 2 5 vCPU 10 GB 96 GB SSD Node.js PM2 secondary (5 workers), Puppeteer report worker
4 DB Primary 5 vCPU 20 GB 360 GB NVMe PostgreSQL 16 primary + pgBouncer, LUKS encrypted, WAL archiving to replica
5 DB Replica 5 vCPU 10 GB 360 GB NVMe PostgreSQL streaming replica (hot standby), daily backup to offsite / NAS, audit read queries
Total 22 vCPU 55 GB RAM ~972 GB

Security measures included

  • LUKS full-disk encryption on both DB nodes (prevents data extraction from stolen drives)
  • WireGuard VPN — all admin SSH access goes through bastion only; DB nodes have no public IP
  • ModSecurity WAF on nginx (OWASP Core Rule Set) — blocks SQLi, XSS, scanner probes
  • Fail2ban on all nodes — auto-bans repeated auth failures
  • PostgreSQL streaming replication with WAL archiving — RPO < 1 minute, RTO < 5 minutes on failover
  • Automated nightly pg_dump encrypted with GPG, rotated weekly to offsite NAS or object store
  • UFW firewall rules: LB accepts 443/80 from internet; app nodes accept only from LB; DB nodes accept only from app nodes on port 5432
  • All inter-node traffic on a private VLAN / internal subnet (no public IPs on app/DB nodes)
  • Redis password-protected, bound to localhost or private NIC only
Failover behaviour If App Server 1 dies: nginx upstream marks it unhealthy, all traffic shifts to App Server 2 — zero manual intervention. If DB Primary dies: promote Replica via pg_ctl promote (or Patroni for fully automatic), update pgBouncer target — estimated manual RTO ~5 minutes, or ~30 seconds with Patroni.

Why pgBouncer is mandatory at this scale

Node.js with 7 workers × ~50 pg-pool connections each = up to 350 DB connections. PostgreSQL forks a process per connection; 350 processes at 10 MB each = 3.5 GB RAM just for connection overhead. pgBouncer multiplexes all 350 app connections onto ~30 actual PostgreSQL connections, keeping DB RAM usage in check.

Phase 2 scaling triggers — watch these metrics

  • CPU sustained > 70% on app servers → add another app node (horizontal scale, zero config change needed)
  • PostgreSQL query p99 latency > 200 ms → add read replica, offload analytics queries
  • Report queue depth > 20 pending jobs → add a third report worker node
  • DB storage > 70% full → provision and online-extend PostgreSQL tablespace to new volume
  • RabbitMQ message redelivery rate rising → scale consumer workers, not the broker
Note on Cloudinary As long as Cloudinary handles all file uploads (evidence photos, documents), the local storage numbers above stay accurate. If you migrate to MinIO in Phase 2, add 4 × 4.8 TB HDD nodes (MinIO erasure-coded cluster) to the Delhi 2-B setup — this is already reflected in the Phase 2 line.
