HEADLINE — C1: DCP/higher levels saw near-empty records (CRITICAL, verified)
═══════════════════════════════════════════════════════════════════════════════
Not a rendering bug and not data loss: the backend was deleting the fields on the
way out, exactly as configured. config/contracts/ops_chain.json whitelisted only
23 field keys for DISTRICT (15 for HQ), and levelContracts.service.js strips every
domain key not on that list — including each persons[i].data and properties[i].
The contracts were authored as stubs while masking was a silent no-op; Integration 5
(2026-07-20) turned masking ON without revisiting them.

The whitelist predicts every reported symptom exactly (act/section, major/minor head,
occurrence block, complainant/victim/accused/property blank; ARREST showing only the
arrestee's name; UIDB only place+date of body found; MISSING only date+status).
Confirmed in the tester's own logs: "masking applied ... visibleKeyCount:23,
personCount:0" — 3,662 masking events in one session.

Fix (per user ruling: full record for DISTRICT/ACP/JCP/SCP, summary only at HQ):
  - levelContracts.service.js: resolveMasking() treats a ["*"] contract as "full
    record" (same fail-open path already used for PS roles). Chosen over deleting
    rows so aggregate_definitions survive and workflow.engine.js's DIRECT_HQ route
    lookup — which reads these same rows — is untouched.
  - ops_chain.json: DISTRICT -> ["*"]; new LDC_DIST_JCP_ALL + LDC_JCP_SCP_ALL
    wildcards (also retires the LEVEL_FALLBACK hack that routed JCP/SCP onto HQ's
    even smaller 15-key list). LDC_DIST_HQ_ALL deliberately unchanged.
  ⚠ Requires `npm run sync-config` after checkout.

DATA-LOSS AND INTEGRITY FIXES
═══════════════════════════════════════════════════════════════════════════════
C16 — properties silently wiped on update (records.service.js)
  32 "upsertProperties: FULL WIPE" events in the tester's logs. upsertPersons got a
  delete-to-zero guard in the 2026-07-23 batch; properties never did, so the same
  frontend race wiped them. Guard now matches the persons one. Accepted trade-off
  (same as ratified decision D1 for persons): clearing ALL properties via edit is
  impossible until an explicit frontend "clear" affordance exists.
  Verified: PUT with properties:[] on a record with a property -> row survives.

C17 — schema drift crashed the tester's DB (migrations/20260726000001)
  "value too long for type character varying(10)" on every TRANSGENDER person save.
  ROOT CAUSE: an earlier session EDITED AN ALREADY-APPLIED MIGRATION IN PLACE
  (widening persons.gender in 20260711000004, deleting the standalone ...000007).
  Fresh DBs are fine; any DB provisioned from the original file keeps the narrow
  column FOREVER because knex records that migration as run. Fixed with a forward,
  idempotent, no-op-on-healthy repair migration. Also restores 'INVOLVED' on
  record_properties.status.
  ⚠ Deployment: affected environments need `npm run db:migrate`. NOT a db:reset —
    testers keep their data.
  RULE: never fix drift by editing an applied migration again.

C8 — duplicate-FIR protection was completely inert (records.service/normalize)
  fir_details has UNIQUE(ps_id, fir_year, fir_no), but fir_year was NULL on all 28
  rows and Postgres treats NULL as always-distinct, so the constraint could never
  fire. Proven: two same-PS/same-FIR rows coexisted; setting fir_year made Postgres
  reject them immediately. fir_year is now derived on create AND update.
  (Pre-existing duplicates in the DB are cross-PS, which is legitimate — FIR numbers
  are per-station; that is why the constraint is composite.)

C19 — workflow could never reach HQ without JCP+SCP (config only, E2E-verified)
  Found by driving the chain end-to-end, not by reading code. The only route to
  HQ_RECEIVED was DISTRICT -> JCP -> SCP -> HQ, so a DCP approval parked records at
  JCP_REVIEW awaiting roles that are not staffed — 13 were already stranded silently.
  workflow.engine.js already implemented a DIRECT_HQ short-circuit that had never been
  switched on. Set LDC_DIST_HQ_ALL.route = DIRECT_HQ (config only, zero code); JCP/SCP
  transitions stay dormant in config for when those roles go live.
  Verified: HC create -> submit -> SHO approve -> DCP approve now lands HQ_RECEIVED;
  transition ledger clean; `npm run audit:verify` hash-chain intact before and after;
  record appears in HQ's list. Pre-stranded records left as-is (dev data, user ruling).

C9 — property minor-category silently NULLed for arms/drugs (records.normalize)
  resolvePropertyMinorCategory only consulted ref.other_property_items, never the
  arms/drugs/jewelry/currency-specific ref tables. Against a real ARREST sample,
  11 of 15 filled property rows could never resolve — major landed, minor dropped
  silently. This is most of the tester's "property category nhi aaya".
